# 画像埋め込みQRコード最適化

固定文字列を保持し、変更してよいASCII文字列を探索して、元画像に近い正規QRコードを作ります。さらに、同じ文字列に読み取れることを検証した加工版も別に表示・保存できます。画像・文字列はブラウザ内で処理します。

## 使い方

1. [アプリ](./)を開くか、[単一HTML版](./image-qr-optimizer.html)を保存して開きます。単一HTML版は通信なしで動作します。
2. 元画像と固定する文字列を指定します。可変部分には、変更してよい文字・長さを設定します。URLの例は固定部分 `https://example.com/#` と可変部分の組み合わせです。実際のURLで変更してよい箇所を確認してください。
3. 通常は「指定した文字種を使う（Byte）」で、URLとして有効な文字種と長さを設定します。URLを一文字も変えられない場合は、可変部分を削除してURL全体を固定します。
4. 必要な領域をブラシ・矩形・円形で指定します。「できるだけ黒／白」は目標、「絶対黒／白」は必ず満たす条件です。重要度0の領域は探索スコアから除外します。
5. 「生成する」を押し、検証を通過した候補を比較します。初期値はURL-safe文字128文字・ECC M・49×49マス、マスク8通り、20秒、加工の自動モードです。「生成後に加工版も作る」が有効なら、表示数より多い候補を加工・検証し、完成画像のスコア順に並べます。候補一覧にも加工版を表示します。
6. 正規版・加工版のそれぞれのボタンからPNGまたはSVGを保存します。実際に復号される文字列は両方同じです。白い余白は4マス以上です。

固定部分はUTF-8の日本語に対応します。可変部分はASCIIで、複数配置でき、禁止文字も指定できます。任意の長い数字列が使える場合に限り、Numeric方式を選択できます。この方式では、禁止文字を除いた許可集合が0〜9をすべて含む可変部分だけを数字に絞ります。「このサイズで数字を最大限使う」は、その最後の可変部分の長さも容量いっぱいに変更する操作です。通常の生成や加工はこの変更を必要としません。

## 生成後の加工版

正規QRの生成・検証後、正規版の文字列をそのまま読み取れる加工版を作ります。読み取り対象のURL、文字種、文字数、Version、ECC、Maskは変えません。元の正規版も残します。

| モード | 描画と選び方 |
| --- | --- |
| 自動（初期値） | マス加工、マス加工と画像描画の組み合わせ、中央を変更しない画像描画を試し、検証できた完成画像を比較 |
| 元画像の色を残す | QRの中央部分を黒白で残し、周囲に3倍解像度の元画像を描く。文字列全体が固定でも利用可能 |
| 白黒の濃淡を残す | 周囲を明るさに合わせたグレーで描く。写真の濃淡を保持 |
| マス単位で加工する | マス全体を目標の白黒へ変更する従来方式 |

画像モードでは、中央の幅を37.5%から順に50%／62.5%／75%／87.5%へ太くし、検証を通る描画を探します。色の描画で見つからない場合は自動モードで白黒描画も試します。画像描画で改善できなければ検証済みのマス加工へ戻り、その理由を表示します。位置検出などの構造・余りビット・絶対指定・重要度0のマスは、中央だけでなくマス全体を保持します。

しきい値は中央に使う白黒目標を決めます。画像モードの周囲には、切り出し・位置・拡大率・コントラスト・明るさ・反転を適用した元画像の色と濃淡を残します。手動の「できるだけ黒／白」は周囲の画像にも反映します。[Halftone QR Codes](https://cgv.cs.nthu.edu.tw/projects/Recreational_Graphics/Halftone_QRCodes)の画像と読み取りパターンを組み合わせる方向性を参考にしていますが、同論文の学習済み辞書や読み取りモデルを再現した実装ではありません。

- 誤り訂正（RS）の各ブロックについて、変更した8bit単位の語数を管理します。同じ語の中で複数マスを変更しても、使う訂正能力は1語分です。[DENSO WAVEの説明](https://www.qrcode.com/en/about/error_correction.html)に従い、訂正語数から訂正可能な誤り語数を計算します。
- 訂正可能な語数の0%／50%／70%／90%を加工の上限として選択できます。初期値は70%。どのブロックにも少なくとも1語分の余力を残します。この割合は塗れる面積の割合ではありません。画像モードで0%を選ぶと、中央のマスを一つも変更せず周囲だけを描きます。
- 位置検出・位置合わせ・タイミング・形式・Version情報と余りビットを保持します。絶対黒白の指定と重要度0のマスも変更しません。
- マス加工は1マス2／4／8px、画像描画は4／8／12px・余白4マスの画像からjsQRで復号し、正規版とバイト列が完全一致する場合だけ採用します。画像描画では8pxの完成画像を面積平均で50%へ縮小した画像、分離可能な3×3カーネル `[1,2,1] / 4` でぼかした画像も復号します。
- マス加工の検出に失敗したら加工する語数を減らし、画像描画の検出に失敗したら中央を太くして再検証します。改善する検証済みの加工版がなければ、正規版の保存を提供します。
- 保存時にも、指定した寸法・余白の画像を読み戻して復号します。加工版のファイル名には `-artistic-` が付きます。
- 初めに選んだ加工箇所を、同じブロックの別の語と入れ替えて濃淡のまとまりを改善します。訂正予算は増やしません。読み取り失敗で加工量を減らした場合も、元の正規版より探索スコアが改善する候補だけを提供します。

加工量と残る訂正余力は結果の詳細に表示します。画像モードの語数と残る余力は、中央のマスの誤りについての理論値です。周囲の画像による読み取りへの影響は、実際の完成画像・縮小・ぼかしの復号で確認します。自動検証に成功しても、実機カメラ・印刷・汚れ・遠近変形など任意の条件での読み取りを保証するものではありません。

## 精度の改善

- **QR容量を絵に使う**：数字3文字を10bitで符号化し、初期求解ではそのうち9bitを有効な数字の範囲で変更します。同じQRサイズに多くの自由度を入れられます。マスクと目標に応じて固定するbitを選び、必要に応じて0〜999全体から絶対指定を満たす候補・局所改善を探します。末尾1〜2文字にも対応します。この方向性は[QArt Codes](https://research.swtch.com/qart)を参考にしています。
- **指定をそのまま保持**：元画像、画像変換、ソフト目標、Float32の重要度、絶対指定を別々の状態として管理。長さ・Versionの比較や中断で失いません。重みをキャンバスの色から復元しません。
- **文字集合を広く利用**：初期求解は許可集合内の最大アフィン部分空間を厳密に選択。その後は許可文字全体による局所改善を行います。初期集合で絶対指定が解けない場合も、7bitの線形式と許可集合による探索を試みます。
- **Byteの初期集合を画像に合わせる**：「画像に合わせて文字の初期集合を選ぶ」が有効なら、可変部分の文字位置ごとに、許可集合内の部分空間と初期文字を選びます。データのマスを目標に合わせる効果と、失う自由度のコストを比較するヒューリスティックです。固定部分・許可文字・禁止文字・文字数・符号化方式は変更しません。初期集合を手動指定した部分は自動変更の対象から外し、絶対指定が元の集合で解ける場合はその解を捨てません。
- **初期の判断を見直す**：重要度順の初期求解だけで止めず、絶対指定を守る自由度で単独・ペア変更を試します。残存自由度が8bit以下なら、時間内で全組合せを比較します。
- **濃淡を探索の指標にする**：画素の重要度付き一致と、2・4・8マス単位の濃淡誤差を組み合わせます。評価割合0なら画素一致のみです。「探索スコア」は候補を並べる指標で、人による見た目の再現率ではありません。
- **画像描画そのものを測る**：画像モードの「濃淡一致」は、1マス8pxの完成画像と目標の明るさの平均絶対差を255で正規化し、1から引いたものです。白い余白は除き、構造部分は含めます。2・4・8マス単位の濃淡差と組み合わせて候補を並べます。中央のマス一致とは別の指標で、写真や色を二値化して見た目の改善を水増ししません。
- **見え方の弱点を表示**：結果には全マスの画素一致、目標の黒領域を黒くできた割合、背景の白領域へ黒が混入した割合を分けて表示します。黒領域の再現は高いほど、背景への黒混入は低いほど目標に近くなります。これらは重要度を掛けない集計です。
- **完成画像で候補を比較**：加工前の良さと、訂正予算内で改善できそうな量の両方を使って候補を保持します。加工版が有効な場合は、最大で表示候補数の3倍（最低8候補）の正規版・加工版を検証し、実際の完成画像で表示順位を決めます。予測スコアだけで加工版を採用しません。加工を無効にした場合は正規版のスコア順です。
- **範囲を比較**：Mask 0〜7、4方向、指定Version範囲、可変長の粗探索と上位長さ近傍の細探索に対応。1条件で絶対指定が解けなくても他の条件を続けます。
- **計算を共有**：RS符号の線形性から差分を作り、マスク間で共有。実エンコーダとのセルフテストも実行します。従来の「1長さ・1パス・16サンプル・マスク比較OFF」への自動変更は廃止しました。

Versionを変えるとき、目標と重要度は元の編集座標から投影します。絶対指定は重なるすべてのマスへ投影し、絶対黒と白が重なったVersionは除外します。選択範囲を黙って捨てたり緩めたりしません。

時間は目安です。計算単位の完了と最終検証には追加時間がかかることがあります。中断はWorkerを停止し、入力を保持します。探索はヒューリスティックで、全体最適解や、見つからなかった場合の解の不存在を保証しません。

## 出力の検証

正規版の各候補に次の検証を必須にしています。加工版には上記の別の検証を適用し、「エンコーダと差分0」「RS誤り0」として扱いません。

| 検証 | 合格条件 |
| --- | --- |
| 固定文字列・許可文字 | 固定部分のバイト列が一致し、可変部が許可集合内 |
| 絶対黒・絶対白 | 保存用の白黒配置で全件達成 |
| 元エンコーダ | 求解結果との白黒差分0 |
| 独立エンコーダ（Nayuki） | Byte／Numericの区切り・Version・ECC・Maskを揃えて差分0 |
| 出力画像の再読込 | モジュール中心を読み戻して差分0 |
| 独立デコーダ（jsQR） | 画像から検出・復号したバイト列が完全一致 |
| RSブロック | 各ブロックの誤り語数0、非零シンドローム0 |

PNG／SVG保存時は、選んだ寸法と余白でもCanvasの画像を再読込・復号します。画像モードのSVGは色と中央模様をピクセル単位のベクトルで描き、同じ寸法のPNGと全画素が一致します。外部画像を参照しません。自動テストではPNGへの符号化・再読込と回転・縮尺も確認します。実機カメラ、印刷、汚れ、遠近変形での読み取り評価は別途必要です。

## 再現できる検証

```sh
npm ci --prefix tools/image-qr --ignore-scripts
npm --prefix tools/image-qr test
node tools/build-image-qr.mjs --check
npm --prefix tools/image-qr run benchmark
npm --prefix tools/image-qr run benchmark:numeric
npm --prefix tools/image-qr run benchmark:artistic
npm --prefix tools/image-qr run benchmark:completion
npm --prefix tools/image-qr run benchmark:picture
tools/image-qr/node_modules/.bin/playwright install --with-deps chromium
npm --prefix tools/image-qr run test:browser
```

Node.js 24を使用。CIで構文、回帰テスト、単一HTMLの再現性と実際のChromiumブラウザを確認します。テストには実エンコーダとの写像一致、全Version／ECCのRS構成、独立復号、ByteとNumericの混在、最大容量・桁数境界・先頭ゼロ、文字集合の取りこぼし、入力状態の保持、オフラインWorker、中断後の再生成を含みます。jsdomのUIデータフローテストではCanvasを模擬します。別のブラウザテストでは通信を切り、PNG画像の入力、ネイティブCanvasとWorker、実際のPNG/SVGダウンロード、SVGのラスタライズ後の復号、中断・再生成、1280pxと390px幅での横はみ出しの有無を検証します。

加工版は4つのECCレベル・4方向、構造と絶対指定の保持、ブロックごとの予算超過、復号失敗時の非出力、独立したPNG／SVGダウンロードと復号文字列の一致を回帰テストしています。画像描画は色付きUTF-8 URL、マス全体の保護、0%予算、描画情報の不正指定、検証済みマス加工への復帰、完成画像によるマスク選択を確認します。実ブラウザでは色付きPNGと実際のSVGの全画素一致、0%予算の白黒画像、オフライン実行も確認します。

[画像描画モードの比較](./verification/picture/README.md)では、同一の正規QR・全文字列・Version・ECC・Maskを保ったまま、以前のマス加工と画像描画を比較します。図形に加えてNASAの公開写真を含みます。中央のマス一致と、実際の画像の濃淡一致は分けて記録します。

[正規版と加工版の比較](./verification/artistic/README.md)では、QRの文字列・マス数・ECC・Maskをすべて揃えたまま加工の効果を確認できます。可変部分なしの固定URLも含みます。

[完成画像で選ぶ探索の比較](./verification/completion/README.md)では、以前のエンジンと改善版を、同じ固定文字列・可変文字種・128文字・Byte方式・Version・ECC・探索予算で比較します。変更してよい可変部分とマスクの探索結果は異なります。任意画像の一般的な再現率や全体最適解を示す測定ではありません。

[数字方式の比較結果と検証画像](./verification/numeric/README.md)では、円形・斜線・ハートを同じ49×49マス、ECC M、固定URL、20秒の予算で比較します。両方式で容量を最大限使うため、可変部分の文字数は異なります。

[以前のByte方式の比較](./verification/README.md)も残しています。こちらは旧貪欲法と追加探索の比較で、画素一致の改善は0.08〜0.67ポイントでした。数字用符号化の改善幅とは別の記録です。

## ファイル構成と更新

- `assets/image-qr-engine.js`：文字集合解析、QR写像、最適化、検証、SVG生成。
- `assets/image-qr-worker.js`：計算の実行と進捗通知。
- `assets/image-qr-ui.js` / `assets/image-qr.css`：入力状態、画像変換、領域編集、画面、保存。
- `assets/vendor/image-qr/`：独立エンコーダ・デコーダとライセンス、固定したソース版。
- `tools/image-qr/`：回帰テスト・比較用の旧方式とベンチマーク。
- `tools/build-image-qr.mjs`：すべての依存とWorkerを埋め込んだ単一HTMLの生成。

ソースを変更したら `node tools/build-image-qr.mjs` を実行し、生成した `image-qr-optimizer.html` も一緒にコミットします。外部CDN、追加ファイル、サーバーは単一HTML版に不要です。Jekyll版は既存のGitHub Pagesプレビューに対応しています。
